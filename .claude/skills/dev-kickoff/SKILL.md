# 개발시작하기 (dev-kickoff)

아이디어 → PRD → 스프린트 → 스토리로 내려가는 대화형 기획 워크플로우.

핵심 원칙: **사용자가 말하지 않은 것을 혼자 결정해서 문서로 굳히지 말 것.** 이 워크플로우의 가치는 산출물의 분량이 아니라, 질문을 통해 사용자 머릿속의 암묵적 맥락을 끌어내는 데 있다. 대신 질문만 끝없이 던져서도 안 된다. 모르면 물어보고, 물어볼 만한 가치가 없는 것(관례적 기본값)은 스스로 정하고 "이렇게 잡았다"고 알린다.

## 시작

이 스킬이 켜지면 **처음 한 마디는 항상 이것이다:**

> 어떤걸 만들고 싶니?

이미 사용자가 아이디어를 설명하며 이 스킬을 불렀다면 그 문장은 생략하고, 들은 내용을 2~3줄로 되짚은 뒤 바로 1단계 질문으로 들어간다.

## 진행 방식 (모든 단계 공통)

- **한 번에 3~5개 질문.** 번호를 붙여서, 사용자가 "1번은 A, 3번은 몰라"처럼 골라 답할 수 있게 한다. 질문 20개를 쏟아내면 사용자는 답을 포기한다.
- **질문마다 추천 기본값을 함께 제시한다.** ("보통은 X로 갑니다. 다르게 가고 싶으신가요?") 사용자가 "너가 정해"라고 하면 즉시 그 기본값으로 확정하고 다음으로 넘어간다.
- **모른다고 하면 캐묻지 않는다.** 가정으로 기록하고(`가정:` 표시) 나중에 검증할 항목으로 남긴다.
- 답을 들으면 **먼저 반영한 결과를 보여주고**, 그 다음에 새 질문을 한다. 질문 → 답 → 갱신된 문서 → 다음 질문의 리듬을 유지한다.
- 사용자가 쓰는 언어로 대화한다. 한국어로 말하면 산출물도 한국어로 쓴다.

## 1단계 — PRD를 위한 인터뷰

목적: 무엇을, 누구를 위해, 왜, 어디까지 만드는지를 합의한다. **어떻게 만들지(기술 구현)는 아직 묻지 않는다.**

다음 축을 순서대로 훑되, 사용자의 답에서 이미 드러난 축은 건너뛴다. 한 번에 한두 축씩만 물어본다.

1. **문제와 사용자** — 누가 쓰나? 지금은 그 사람이 이 일을 어떻게 해결하고 있나? 뭐가 제일 불편한가?
2. **핵심 가치 한 줄** — 이게 없으면 안 되는 이유. "이 제품은 ___한 사람이 ___를 ___하게 해준다."
3. **핵심 사용 흐름** — 사용자가 앱을 열고 나가기까지 가장 중요한 한 가지 시나리오를 처음부터 끝까지.
4. **범위 경계** — MVP에 반드시 있어야 하는 것 / 있으면 좋은 것 / 이번엔 안 하는 것. **"안 하는 것"을 꼭 물어본다.** 범위를 자르는 결정이 스프린트 개수를 결정한다.
5. **성공 기준** — 뭘 보면 성공인지. 숫자가 없어도 좋다("나 혼자 매일 쓰게 되면 성공").
6. **제약** — 기한, 투입 인원, 예산, 이미 정해진 기술 스택이나 붙어야 하는 기존 시스템.
7. **데이터와 외부 연동** — 어떤 데이터를 다루나? 개인정보/결제/로그인이 있나? 외부 API를 쓰나?
8. **비기능 요건** — 동시 사용자 규모, 응답 속도, 오프라인 지원, 접근성, 보안 수준. 대부분 기본값으로 충분하니 특별한 요구가 있을 때만 깊게 판다.
9. **리스크** — "이게 안 되면 프로젝트가 무너진다" 싶은 미지수.

### 언제 인터뷰를 끝내는가

아래를 스스로 채점해서 대부분 "예"면 인터뷰를 멈추고 PRD를 쓴다. 완벽한 정보를 기다리지 않는다 — 남은 빈칸은 `가정:`으로 적고 스프린트에서 검증하면 된다.

- 핵심 사용 흐름을 내가 처음부터 끝까지 다시 말할 수 있는가?
- MVP에 들어가는 기능 목록을 셀 수 있는가?
- "이번엔 안 하는 것"이 최소 한 개는 정해졌는가?
- 성공을 판단할 기준이 있는가?
- 기한/인원/스택 중 아는 것이 하나라도 있는가?

끝낼 때는 사용자에게 이렇게 알린다: "이 정도면 PRD를 쓸 만큼 모인 것 같아. 지금 정리해볼게 — 빠진 게 있으면 말해줘."

### PRD 형식

`docs/prd.md`에 저장하고(사용자가 다른 위치를 원하면 그곳에), 대화에도 요약을 보여준다.

```markdown
# PRD: [제품명]

## 1. 한 줄 요약
## 2. 문제 정의
## 3. 대상 사용자
## 4. 핵심 사용 흐름
## 5. 범위
### MVP에 포함
### 나중에 (Out of scope for now)
## 6. 성공 기준
## 7. 제약과 전제
## 8. 데이터 / 외부 연동
## 9. 비기능 요건
## 10. 리스크와 미해결 질문
```

`10. 리스크와 미해결 질문`에는 인터뷰에서 남은 `가정:` 항목을 그대로 옮긴다. 이게 다음 단계의 질문 씨앗이 된다.

## 2단계 — 스프린트 계획

PRD를 스프린트로 쪼갠다. 스프린트 개수는 정해진 답이 없다 — 보통 3~6개면 MVP가 나온다. 스프린트가 10개를 넘으면 범위를 너무 안 잘랐다는 신호이니 사용자에게 범위 축소를 제안한다.

### 쪼개는 기준 (이 순서로 판단한다)

1. **의존성** — 뒤 작업이 앞 작업의 산출물을 필요로 하면 순서가 강제된다.
2. **리스크 선점** — "이게 안 되면 프로젝트가 무너진다"는 미지수는 **가능한 앞 스프린트로** 당긴다. 늦게 터지는 실패가 제일 비싸다.
3. **데모 가능성** — 각 스프린트 끝에는 사용자에게 보여줄 수 있는 무언가가 있어야 한다. "DB 스키마만 만드는 스프린트"는 나쁜 스프린트다. 얇더라도 세로로 관통하는(end-to-end) 한 조각이 낫다.
4. **크기** — 한 스프린트는 대략 비슷한 무게로. 사용자가 기한/인원을 말했다면 그 단위(1주, 2주)에 맞춘다. 말하지 않았다면 "작업 단위"로 두고 기간은 비워둔다.

### 스프린트 형식

각 스프린트마다:

```markdown
## Sprint N — [이름]
- **목표**: 이 스프린트가 끝나면 무엇이 가능해지는가 (사용자 관점 한 문장)
- **포함 작업**: 3~7개 항목
- **완료 기준(DoD)**: 무엇을 보면 끝났다고 할 수 있는지
- **의존**: 앞의 어느 스프린트에 기대는지
- **이번에 걷어내는 리스크**: 있으면
```

### 구성 근거 설명 (필수)

스프린트 표를 보여준 다음, **왜 이렇게 잘랐는지를 반드시 설명한다.** 사용자가 순서를 바꾸거나 반대하려면 근거를 알아야 하기 때문이다. 설명은 스프린트별 한두 줄이면 충분하다:

> Sprint 1을 로그인 대신 [핵심 기능]으로 잡은 이유는, 이 제품에서 제일 불확실한 게 [X]라서 그걸 먼저 깨보는 게 낫다고 봤어. 로그인은 검증된 영역이라 Sprint 3으로 미뤘고.

### 애매하면 다시 묻는다

스프린트를 짜다 보면 PRD에 없던 판단이 필요해진다. 혼자 결정하지 말고 이 시점에 다시 질문한다. 자주 나오는 것들:

- 우선순위 충돌: "A와 B 중 뭐가 먼저 필요해?"
- 인증/권한을 언제 넣을지
- 데이터 마이그레이션이나 기존 시스템 연동 시점
- 배포/운영 환경을 언제 세울지
- 디자인 완성도를 어느 스프린트에서 올릴지

질문 후 답을 받으면 **스프린트 계획 전체를 다시 정리해서 보여준다.** 바뀐 부분만 말하지 말고 갱신된 전체 목록을 제시해야 사용자가 전체 그림을 잃지 않는다. 이 루프는 사용자가 "좋아, 이대로 가자"라고 할 때까지 반복한다.

`docs/sprints.md`에 저장한다.

## 3단계 — 스토리 구체화 (스프린트 하나씩)

**중요: 모든 스프린트를 한꺼번에 스토리로 만들지 않는다.** 뒤 스프린트는 앞 스프린트를 하면서 알게 된 것 때문에 반드시 바뀐다. 미리 다 써두면 그 노력이 버려지고, 사용자는 읽지도 않을 문서 더미를 받게 된다.

시점은 이렇다: **한 스프린트를 시작할 때 그 스프린트만 스토리로 내린다.** 그 스프린트가 끝나면 회고를 겸해 다음 스프린트의 스토리를 만든다.

스프린트 계획이 확정되면 사용자에게 이렇게 묻는다: "스프린트 계획은 확정됐어. Sprint 1의 스토리부터 만들어볼까?"

### 스토리 형식

```markdown
### S1-01 — [제목]
- **사용자 스토리**: [역할]로서 [무엇]을 하고 싶다, [왜냐하면]
- **인수 조건**:
  - Given [상황] / When [행동] / Then [결과]
  - (2~4개)
- **기술 메모**: 건드릴 파일·모듈, 선택한 접근
- **크기**: S / M / L
- **의존**: 선행 스토리 ID
```

인수 조건은 **테스트로 옮길 수 있을 만큼 구체적으로** 쓴다. "로그인이 잘 되어야 한다"는 인수 조건이 아니다. "잘못된 비밀번호를 3회 입력하면 계정이 5분간 잠긴다"가 인수 조건이다.

### 스토리도 질의응답으로 만든다

스프린트를 만들 때와 같은 리듬이다. 초안을 보여주고, 애매한 지점을 질문하고, 답을 받아 갱신한 전체 목록을 다시 보여준다. 스토리 단계에서 자주 걸리는 애매함:

- 에러/예외 상황에서 사용자에게 뭘 보여줄지
- 입력 검증 규칙(길이, 형식, 중복 허용 여부)
- 빈 상태(데이터가 하나도 없을 때) 화면
- 권한이 없는 사용자가 접근했을 때
- 어디까지 자동화하고 어디부터 수동으로 둘지

`docs/stories/sprint-1.md`처럼 스프린트별 파일로 저장한다.

### 스프린트가 끝나면

다음 스프린트 스토리로 넘어가기 전에 짧게 묻는다: "Sprint 1 하면서 알게 된 것 중에 뒤 스프린트 계획을 바꿔야 할 게 있어?" 답에 따라 `docs/sprints.md`를 갱신한 뒤 다음 스프린트 스토리를 만든다.

## 하지 말아야 할 것

- 인터뷰를 건너뛰고 PRD를 혼자 완성하기 — 사용자가 고칠 게 너무 많아져서 오히려 느려진다.
- 질문 15개를 한 번에 던지기.
- 스프린트 구성 근거를 생략하기 — 근거 없는 계획은 사용자가 검증할 수 없다.
- 모든 스프린트의 스토리를 미리 다 쓰기.
- 사용자가 "이대로 가자"라고 하지 않았는데 코드를 쓰기 시작하기. 이 스킬의 끝은 합의된 문서이지 구현이 아니다. 구현은 사용자가 "이제 만들자"라고 할 때 시작한다.
