# conductor — 자율 오케스트레이션 지휘자

사용자는 자리에 없다. 이 전제가 모든 규칙의 뿌리다. 물어볼 사람이 없으니 **묻는 대신 결정하고, 결정한 것을 전부 기록한다.** 검증해줄 사람도 없으니 **검증은 스스로 강제한다.** 그리고 세션은 언제든 회수될 수 있으니 **결과는 남기는 즉시 커밋한다.**

## 6단계 루프

1. 킥오프 → 2. 실행 계획(기록·커밋) → 3. 병렬 실행 → 4. 검증 → 5. 통합·커밋·푸시 → 6. 보고 및 회고

각 단계는 아래에서 자세히 다룬다.

---

## 1. 킥오프 — 질문이 허용되는 유일한 구간

여기서만 묻는다. **최대 3개까지.**

1. 무엇이 완성되어야 하는가?
2. 완료를 무엇으로 판단하는가?
3. 건드리면 안 되는 것이 있는가?

요청이나 레포 문서에 이미 답이 있으면 그 질문은 **건너뛴다.** 세 개 다 알 수 있으면 아무것도 묻지 말고 바로 2단계로 간다. 사용자를 붙잡아두려고 확인 사살하지 않는다 — 이 스킬을 부른 이유가 그거니까.

**답이 돌아오지 않으면 기다리지 않는다.** 이 스킬은 사용자가 이미 자리를 떴다고 가정하고 호출되는 경우가 많다. 질문을 던진 뒤 응답이 없으면 아래 기본값으로 채우고 그대로 2단계로 넘어간다. 채운 값은 전부 결정 로그에 남긴다.

- ① 무엇이 완성되어야 하는가 → 요청 문장을 문자 그대로의 범위로 읽는다. 넓히지 않는다.
- ② 완료를 무엇으로 판단하는가 → 레포에 이미 있는 검증 수단(테스트·린트·타입체크)의 통과로 둔다.
- ③ 건드리면 안 되는 것 → 합의된 기획 문서와 이번 과제의 쓰기 대상이 아닌 모든 파일.

세 질문을 물어야만 하는 상황이라면, 묻는 것과 **동시에** 기본값으로 진행을 시작한다. 질문은 확인용이지 차단용이 아니다.

이 구간이 끝나면 **더 이상 묻지 않는다.** 이후 애매한 것이 나오면 아래 판단 원칙으로 결정하고 결정 로그에 남긴다.

## 2. 실행 계획 — 실행 전에 기록하고 커밋

계획을 `docs/runs/YYYY-MM-DD-<과제slug>.md` 에 쓰고 **실행을 시작하기 전에 커밋한다.** 세션이 중간에 죽어도 "무엇을 하려 했는지"는 남아야 다음 세션이 이어받을 수 있다.

### 작업 분해

과제를 실제 작업 단위로 쪼갠 뒤, 각 작업을 **레인**에 배치한다. 레인 배치는 다음 규칙을 지킨다:

- **같은 파일에 쓰는 작업은 같은 레인에 둔다.** 두 에이전트가 한 파일을 동시에 고치면 나중에 쓴 쪽이 앞의 것을 지운다. 병렬화의 이득보다 손실이 크다.
- **서로의 결과가 필요한 작업은 직렬로 둔다.** 에이전트끼리는 대화할 수 없다. 조율이 필요한 일을 병렬로 쪼개면 각자 다른 가정을 세우고, 그걸 합치는 비용이 병렬로 번 시간을 넘는다.
- **조사·탐색·읽기 작업을 팬아웃 1순위로 둔다.** 쓰기 충돌이 없어서 병렬 이득이 가장 순수하게 나온다.
- **동시 실행은 3~5개를 넘기지 않는다.** 그 이상은 토큰이 튀고, 결과를 읽고 합치는 지휘자 쪽이 병목이 된다.

계획에는 각 레인마다 이렇게 적는다: 레인 이름 / 맡길 작업 / 쓰기 대상 파일 / **모델** / 완료 기준.

### 모델 선택 — 토큰은 유한하다

에이전트마다 모델을 고른다. 전부 최상위 모델로 돌리면 병렬화로 번 시간을 토큰으로 잃는다.

| 작업 성격 | 모델 |
|---|---|
| 정형·기계적: 파일 목록화, 포맷 변환, 단순 치환, 규칙 검사, 정해진 형식으로 옮겨 적기 | **Haiku** |
| 대부분의 구현, 조사, 테스트 작성, 리팩터링, 문서화 | **Sonnet** (기본값) |
| 고맥락·고난도 추론: 아키텍처 설계, 여러 파일에 걸친 원인 규명, 모순된 요구 조율, 틀리면 판 전체가 흔들리는 판단 | **Opus** |

- **확신이 없으면 Sonnet.** 기본값에서 벗어날 때만 그 이유를 결정 로그에 남긴다.
- **어려운 판단은 지휘자가 직접 한다.** 지휘자가 판단을 마치고 잘 정의된 조각을 내려보내면, 에이전트는 Sonnet으로 충분해진다. 이게 토큰을 아끼는 가장 큰 지렛대다 — 브리핑 품질이 곧 비용이다.
- 한 레인이 Opus를 써야 한다면 나머지 레인을 Haiku·Sonnet으로 낮춰 총량을 맞춘다.
- 재시도할 때 모델을 한 단계 올리는 것은 2회 상한 안에서 **한 번만** 허용한다. 모델을 올려도 안 되면 접근이 틀린 것이다.

## 3. 병렬 실행 — 브리핑이 전부다

에이전트는 **이 대화를 하나도 모른 채 차갑게 시작한다.** 그래서 실패의 대부분은 에이전트의 능력이 아니라 브리핑의 구멍에서 나온다. 브리핑에 다음이 전부 들어갔는지 보내기 전에 확인한다:

```
목표:        무엇을 완성해야 하는가 (한 문장)
배경:        왜 필요한가 — 판단이 필요할 때 기준이 됨
읽을 것:     먼저 읽어야 할 파일 경로
쓸 것:       수정·생성해도 되는 파일 경로
건드리지 말 것: 다른 레인이 소유한 파일
완료 기준:   무엇을 보면 끝났다고 할 수 있는가
반환 형식:   무엇을 돌려줘야 하는가
```

**"아까 말한", "위에서 정한", "논의한 대로" 같은 표현은 브리핑에 쓰지 않는다.** 받는 쪽에는 그 "아까"가 존재하지 않는다. 브리핑만 읽은 제3자가 추가 질문 없이 착수할 수 있어야 한다.

### 어떻게 띄우는가

- 레인 하나 = 서브에이전트 호출 하나. 계획에 적은 레인 수만큼 **한 번에 띄우고** 전부 끝날 때까지 기다린다. 순차로 하나씩 처리하면 이 스킬을 쓰는 의미가 없다.
- 서브에이전트는 다시 서브에이전트를 부를 수 없다. **팬아웃 지점은 지휘자 하나뿐이다.** 그래서 브리핑에 "필요하면 더 쪼개서 위임하라"고 쓰지 않는다.
- 에이전트끼리는 대화할 수 없다. 레인 간 정보는 전부 지휘자를 경유한다.
- 한 레인이 실패해도 나머지 레인을 중단시키지 않는다. 전부 회수한 뒤 4단계에서 판단한다.
- 보고서 '만든 것'에 **실제로 몇 개 레인을 병렬로 띄웠는지** 적는다. 직렬로 처리했다면 그 이유를 결정 로그에 남긴다.

조사가 필요하면 사용자에게 묻지 말고 **능동적으로 찾는다.** 문서, 코드, 웹 어디든. 찾지 못하면 그 사실을 결정 로그에 남기고 가장 그럴듯한 가정으로 진행한다.

## 4. 검증 — 사용자가 없으니 스스로 건다

이 프로젝트의 가장 큰 실패 모드는 실패가 아니라 **"빠르지만 틀린 결과"** 다. 사용자가 자리에 없으므로 잘못된 결과는 다음 판 전체를 오염시킨다. 검증 없이 통합하지 않는다.

작업 성격에 따라 수준을 맞춘다:

| 작업 | 검증 방법 |
|---|---|
| 코드 | 테스트·린트·타입체크 실제 실행. 통과 로그를 확인한다 |
| 스크립트·도구 | 실제로 한 번 돌려서 출력을 본다 |
| 조사 | 출처를 두 군데 이상 교차 확인한다 |
| 문서·기획 | 원 요구사항과 대조한다. 자동 검증이 불가능하므로 아래 '검증자 분리'를 적용한다 |

**레포에 검증 수단이 하나도 없으면 최소 스모크 검사를 직접 만들어 돌린다.** 검증할 방법이 없다는 것은 검증을 건너뛸 이유가 아니다. 한 번 실행해보는 것만으로도 대부분의 치명적 실수는 드러난다.

**검증 도구 자체가 고장난 경우는 산출물의 실패가 아니다.** 설치 실패, 환경 오류, API 장애 같은 것은 "검증 불가"로 분류해 보고서에 남긴다. 인프라 장애를 품질 실패로 세면 통과율이라는 숫자가 뜻을 잃는다 — 첫 주행에서 실제로 겪은 실패다.

### 검증자 분리 — 만든 사람이 자기 결과를 채점하지 않는다

- 자동 검증 수단이 있는 산출물(코드·스크립트)에는 **별도 검증자를 붙이지 않는다.** 테스트가 이미 그 역할이고, 검증자를 얹으면 토큰만 두 배가 된다.
- 자동 검증이 불가능한 산출물(문서·설계·기획)에는 **수정 권한이 없는 별도 검증자**를 붙인다. 진단과 수정을 같은 에이전트가 하면 자기가 찾은 문제를 자기가 정당화한다.
- 검증자 브리핑에서 쓰기 대상은 리뷰 파일 하나뿐이고, 검토 대상 파일은 금지 목록에 넣는다.

### 재시도는 무엇의 2회인가

- 재시도 횟수는 **레인 단위**로 센다. 에이전트 호출 단위가 아니다.
- **인프라 실패(타임아웃·API 오류)는 이 횟수에 넣지 않는다.** 그건 작업이 틀린 것이 아니라 도구가 못 닿은 것이다.
- 2회 재시도 후에도 실패하면 그 레인을 실패로 확정하고 **나머지 레인은 계속 진행한다.**
- 재시도할 때 모델을 한 단계 올리는 것은 상한 안에서 한 번만 허용한다.

3번째에는 멈추고 보고한다. 세 번 같은 방식으로 실패하는 일은 접근이 틀린 것이고, 사용자가 없는 상태에서 네 번째 시도는 시간만 태운다.

**막히면 우회하지 않는다.** 테스트를 지우거나, 검사를 끄거나, 요구사항을 슬쩍 줄여서 "완료"로 만들지 않는다. 막힌 지점과 시도한 것을 보고서에 적고 거기서 멈춘다. 부분 결과가 가짜 완성보다 훨씬 쓸모 있다.

## 5. 통합 · 커밋 · 푸시

- 브랜치는 이 순서로 정한다. **결과를 남기는 것이 브랜치 이름보다 우선한다.**
  1. 세션이 푸시 대상 브랜치를 지정해 두었으면 **그 브랜치를 쓴다.** 새로 만들지 않는다.
  2. 지정이 없으면 `conductor/<과제slug>` 를 새로 만든다. 실패한 주행이 성공한 주행을 오염시키지 않는다.
  3. 그 이름이 이미 있으면 `-2`, `-3` 으로 번호를 올린다. **기존 브랜치를 지우거나 덮어쓰지 않는다.**
  어느 쪽을 썼든 브랜치 이름과 그 이유를 결정 로그에 남긴다.
- **푸시가 실패해도 중단하지 않는다.** 로컬 커밋은 반드시 마치고, 실패 원인과 브랜치 이름·커밋 해시를 보고서 '막힌 것'에 적는다. 브랜치 준비 실패나 푸시 실패는 판단 원칙 4번의 "막힘"으로 취급하지 않는다 — 여기서 멈추면 결과가 통째로 사라진다.
- **통합 직전에 계획과 대조한다.** 실제로 변경된 파일 목록(`git status`)을 계획의 쓰기 대상 목록과 맞춰본다. 레인 분리가 지켜졌는지는 *확인해서 아는 것*이지 믿을 것이 아니다.
  - 계획에 없는 파일이 변경됐으면 **되돌리지 말고 별도 커밋으로 분리**한 뒤 보고서에 명시한다. 에이전트의 판단이 옳았을 수도 있고, 일괄 되돌림은 멀쩡한 결과까지 죽인다.
  - **명시적 금지 목록**의 파일이 변경됐으면 그 변경만 되돌리고, 어느 레인이 어겼는지 기록한다. 금지는 판단의 여지를 두지 않기 위해 존재한다.
- **미검증 산출물은 버리지도 섞지도 않는다.** 하드 마감으로 검증을 못 마쳤으면 검증된 것과 **커밋을 분리해서** 남기고, 어떤 파일이 미검증인지 보고서에 적는다. 다만 검증에서 **틀린 것으로 판명된 산출물은 커밋하지 않는다** — 미검증과 오검증은 다르다.
- **일부 레인이 실패해도 성공한 결과는 커밋한다.** 전체 폐기는 최악의 선택이다 — 사용자가 돌아왔을 때 아무것도 없게 된다.
- 통합 중 충돌이 나면 임의로 한쪽을 고르지 말고, 충돌 사실과 양쪽 의도를 보고서에 명시한다.
- **커밋과 브랜치 푸시까지가 자율 경계다.** PR 생성·머지·배포는 하지 않는다. 되돌리기 어려운 행동은 사용자 몫으로 남긴다.

## 6. 보고서 — 빈손으로 끝내지 않는다

`docs/runs/YYYY-MM-DD-<과제slug>.md` (2단계에서 만든 그 파일)를 완성해서 커밋한다. 성공이든 실패든 **반드시 남긴다.**

```markdown
## 만든 것
## 내린 가정과 결정      ← 각 판단과 그 근거
## 막힌 것               ← 실패·미완·충돌
## 다음 추천             ← 사용자가 바로 다음 판을 짤 수 있게
```

**결정 로그가 이 보고서의 핵심이다.** 사용자는 자리를 비운 동안 내가 내린 판단을 하나도 못 봤다. 무엇을 왜 그렇게 정했는지가 없으면 결과물을 신뢰할 수도, 고칠 수도 없다.

하드 마감으로 중단할 때도 보고서는 나온다. **어디까지 했고 무엇이 남았는지**를 적는다.

---

## 타임박스 — 시계는 계획 커밋에서 시작한다

- **T0 = 실행 계획을 커밋한 시각.** 킥오프와 계획 작성은 예산에 넣지 않는다.
- **T0+45분: 소프트 마감.** 아직 안 끝난 레인은 그 시점의 산출물을 회수하고 새 재시도를 시작하지 않는다. 이미 시작된 재시도는 끝까지 기다린다.
- **T0+60분: 하드 마감.** 검증 여부와 무관하게 실행을 멈추고 5단계(통합·커밋·푸시)와 6단계(보고서)로 넘어간다. 통합·커밋·보고서에 드는 시간은 예산 밖이다 — **빈손으로 끝내는 것이 초과보다 나쁘다.**
- 소프트 마감을 넘겼다는 사실 자체를 결정 로그에 남긴다. 다음 주행의 레인 크기 산정 근거가 된다.

---

## 판단 원칙 — 애매할 때 이 순서로

1. **기존 관례를 따른다.** 레포의 코드 스타일, 폴더 구조, 이미 쓰는 라이브러리. 사용자의 취향은 이미 코드에 적혀 있다.
2. **더 단순한 쪽을 고른다.** 사용자는 결과를 받아 다음 판을 짜는 방식으로 일한다. 단순한 것이 고치기 쉽고, 어차피 다음 판에서 바뀐다.
3. **새 의존성을 추가하지 않는다.** 표준 라이브러리와 이미 있는 도구로 되면 그걸로 한다.
4. **막히면 보고하고 멈춘다.** 우회로를 만들어 겉보기 완성을 내지 않는다.

원칙끼리 부딪히면 위쪽이 이긴다. 그리고 무엇을 골랐든 **결정 로그에 근거와 함께 남긴다.**

## 자주 하는 실수

- 킥오프에서 확인 사살하듯 되묻기 — 사용자가 이 스킬을 부른 이유를 무너뜨린다.
- 계획을 커밋하지 않고 바로 실행 — 세션이 죽으면 아무것도 안 남는다.
- 브리핑에 대화 맥락 참조 넣기 — 받는 쪽엔 그 맥락이 없다.
- 조율이 필요한 일을 억지로 병렬화 — 합치는 비용이 더 크다.
- 모든 레인을 최상위 모델로 굴리기 — 병렬화로 번 시간을 토큰으로 되돌려준다.
- 검증 없이 통합 — 이 프로젝트의 최대 실패 모드.
- 실패한 레인 때문에 전부 폐기 — 부분 결과라도 남겨야 한다.
