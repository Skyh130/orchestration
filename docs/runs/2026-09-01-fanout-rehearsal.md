# 주행 기록: 실제 팬아웃 리허설

- **일시**: 2026-09-01
- **과제**: 서브에이전트를 실제로 병렬 기동해 S1-02(레인 분리 규칙)와 모델 선택 규칙을 실물로 검증한다
- **맥락**: Sprint 1 잔여 항목. 직전 주행에서 레인 분리는 문서로만 존재했다
- **상태**: 계획 기록됨 (실행 전)

## 킥오프

묻지 않았다. 세 질문의 답이 이미 확보되어 있다.

1. 무엇이 완성되어야 하나 → 서로 다른 모델의 에이전트 3개가 동시에 돌아 각자 파일을 만들고, 충돌 없이 통합된다
2. 완료를 무엇으로 판단하나 → 3개 산출물이 모두 존재하고, 쓰기 충돌이 0건이며, conductor 트리거 테스트가 실제로 실행된다
3. 건드리면 안 되는 것 → `docs/prd.md`, `docs/sprints.md`, `docs/stories/`, `.claude/skills/dev-kickoff/SKILL.md`

`.claude/skills/dev-kickoff/SKILL.md` 를 금지 목록에 넣은 이유: 직전 주행에서 결함 2건을 찾았지만 사용자는 그 수정이 아니라 팬아웃 검증을 골랐다. 승인되지 않은 수정이 이 주행에 섞이면 안 된다.

## 실행 계획

| 레인 | 작업 | 쓰기 대상 | 모델 | 선택 이유 |
|---|---|---|---|---|
| A | conductor 스킬의 트리거 테스트 세트 20개 작성 | `evals/conductor/triggers.json` | **Sonnet** | 기본값. 판단이 필요하지만 고맥락 추론은 아니다 |
| B | conductor SKILL.md 적대적 리뷰 | `docs/reviews/conductor-v0.1.md` | **Opus** | 스킬 전문을 읽고 규칙 간 모순·구멍을 찾는 고맥락 추론. 틀리면 이후 스프린트 전체가 흔들린다 |
| C | 테스트 실행 방법 문서화 | `evals/README.md` | **Haiku** | 이미 존재하는 파일과 명령을 정해진 형식으로 옮겨 적는 기계적 작업 |

- 세 레인의 쓰기 대상이 서로 겹치지 않는다 → 병렬 가능
- 세 레인 모두 서로의 결과를 필요로 하지 않는다 → 직렬화 불필요
- 동시 실행 3개 = 상한(3~5) 이내

## 검증 방법

1. 산출물 3개 존재 확인
2. `git status` 로 예상 밖 파일 변경이 없는지 확인 (레인 분리 규칙의 실물 검증)
3. `scripts/trigger_test.py` 로 레인 A의 결과물을 **실제 실행** — 도구는 돌려봐야 검증된 것이다
4. 레인 B의 리뷰 내용을 읽고 실제 결함인지 판별
