# 주행 기록: 실제 팬아웃 리허설

- **일시**: 2026-09-01
- **과제**: 서브에이전트를 실제로 병렬 기동해 S1-02(레인 분리 규칙)와 모델 선택 규칙을 실물로 검증한다
- **맥락**: Sprint 1 잔여 항목. 직전 주행에서 레인 분리는 문서로만 존재했다
- **상태**: 완료. 레인 3개 전부 성공, 쓰기 충돌 0건

## 킥오프

묻지 않았다. 세 질문의 답이 이미 확보되어 있다.

1. 무엇이 완성되어야 하나 → 서로 다른 모델의 에이전트 3개가 동시에 돌아 각자 파일을 만들고, 충돌 없이 통합된다
2. 완료를 무엇으로 판단하나 → 3개 산출물이 모두 존재하고, 쓰기 충돌이 0건이며, conductor 트리거 테스트가 실제로 실행된다
3. 건드리면 안 되는 것 → `docs/prd.md`, `docs/sprints.md`, `docs/stories/`, `.claude/skills/dev-kickoff/SKILL.md`

`.claude/skills/dev-kickoff/SKILL.md` 를 금지 목록에 넣은 이유: 직전 주행에서 결함 2건을 찾았지만 사용자는 그 수정이 아니라 팬아웃 검증을 골랐다. 승인되지 않은 수정이 이 주행에 섞이면 안 된다.

## 실행 계획

| 레인 | 작업 | 쓰기 대상 | 모델 | 선택 이유 |
|---|---|---|---|---|
| A | conductor 스킬의 트리거 테스트 세트 20개 작성 | `evals/conductor/triggers.json` | **Sonnet** | 기본값. 판단이 필요하지만 고맥락 추론은 아니다 |
| B | conductor SKILL.md 적대적 리뷰 | `docs/reviews/conductor-v0.1.md` | **Opus** | 스킬 전문을 읽고 규칙 간 모순·구멍을 찾는 고맥락 추론. 틀리면 이후 스프린트 전체가 흔들린다 |
| C | 테스트 실행 방법 문서화 | `evals/README.md` | **Haiku** | 이미 존재하는 파일과 명령을 정해진 형식으로 옮겨 적는 기계적 작업 |

- 세 레인의 쓰기 대상이 서로 겹치지 않는다 → 병렬 가능
- 세 레인 모두 서로의 결과를 필요로 하지 않는다 → 직렬화 불필요
- 동시 실행 3개 = 상한(3~5) 이내

## 검증 방법

1. 산출물 3개 존재 확인
2. `git status` 로 예상 밖 파일 변경이 없는지 확인 (레인 분리 규칙의 실물 검증)
3. `scripts/trigger_test.py` 로 레인 A의 결과물을 **실제 실행** — 도구는 돌려봐야 검증된 것이다
4. 레인 B의 리뷰 내용을 읽고 실제 결함인지 판별

## 타임박스

30분. 초과 시 완료된 레인만 커밋하고 나머지는 이 파일에 남긴다.

# 실행 결과

## 만든 것

**서브에이전트 3개를 한 번에 띄워 병렬 실행했다.** (직전 주행은 직렬이었다)

| 레인 | 모델 | 산출물 | 토큰 | 소요 |
|---|---|---|---|---|
| A | Sonnet | `evals/conductor/triggers.json` — 트리거 테스트 20개 | 57.9k | 75초 |
| B | Opus | `docs/reviews/conductor-v0.1.md` — 적대적 리뷰 10건 | 79.3k | 366초 |
| C | Haiku | `evals/README.md` — 테스트 실행 문서 | 38.3k | 43초 |

리뷰 결과를 받아 `.claude/skills/conductor/SKILL.md` 에 심각도 높음 4건을 반영했다 (아래 결정 참조).

## 검증 결과

1. **레인 분리 규칙(S1-02) 실물 검증 통과.** 3개가 동시에 도는 동안 `git status` 에 나타난 변경은 배정된 세 경로뿐이었다. 금지 목록(`docs/prd.md`, `docs/sprints.md`, `docs/stories/`, `dev-kickoff/SKILL.md`)은 아무도 건드리지 않았다. 문서로만 존재하던 규칙이 실제 병렬 실행에서 지켜졌다.
2. **모델 선택 규칙 실물 검증 통과.** 기계적 작업(레인 C)을 Haiku로 돌린 결과 Sonnet 레인의 66% 토큰, 57% 시간에 요구한 6개 항목을 모두 충족했다. 문서에 적힌 인자 이름 6개가 `scripts/trigger_test.py` 실제 정의와 정확히 일치하는지 대조해 확인했다.
3. **conductor 트리거 테스트 실제 실행: 19/20 (95%), 판정 오류 0건.** 켜지면 안 될 때 안 켜진 비율 100%.
4. **레인 B 리뷰의 사실성 확인.** 발견 4건을 `grep` 으로 원문 대조한 결과 전부 실재하는 공백이었다 (팬아웃 기동·무응답 처리·검증도구 부재·자산화 언급이 본문에 0건).

## 내린 가정과 결정

| 결정 | 근거 |
|---|---|
| 레인을 3개로 잡았다 (상한 5 이내) | 쓰기 대상이 겹치지 않는 독립 작업이 3개였다. 상한을 채우려고 억지로 쪼개면 통합 비용만 늘어난다 |
| 레인 B에만 Opus를 배정 | 스킬 전문을 읽고 규칙 간 모순을 찾는 고맥락 추론. 틀리면 이후 스프린트가 통째로 흔들린다. 나머지는 Sonnet·Haiku로 낮춰 총량을 맞췄다 |
| 레인 B에 SKILL.md 수정을 금지하고 진단만 시켰다 | 진단과 수정을 같은 에이전트가 하면 자기가 찾은 문제를 자기가 정당화한다. 수정 여부 판단은 지휘자가 한다 |
| `dev-kickoff/SKILL.md` 를 금지 목록에 넣었다 | 직전 주행에서 결함 2건을 찾았지만 사용자는 그 수정이 아니라 팬아웃 검증을 선택했다. 승인되지 않은 수정이 이 주행에 섞이면 안 된다 |
| 리뷰 10건 중 **심각도 높음 4건만 반영**하고 나머지 6건은 넘겼다 | 반영한 4건(F-01·F-02·F-03·F-04)은 전부 Sprint 1 스토리(S1-01~S1-05)의 인수 조건이 실제로는 충족되지 않았음을 드러낸 것이라 이번 스프린트 범위다. 나머지 6건은 검증 게이트에 관한 것으로 Sprint 2의 주제다 — 스스로 범위를 넓히지 않는다 |
| 레인 A·C 결과를 레인 B 완료 전에 먼저 커밋했다 | 부분 결과 보존 규칙. 레인 B가 실패했어도 두 산출물은 남는다 |

### 반영한 4건

- **F-01** — 팬아웃을 실제로 어떻게 띄우는지가 없었다. 3단계에 「어떻게 띄우는가」 추가: 레인 수만큼 한 번에 띄운다 / 팬아웃 지점은 지휘자 하나 / 한 레인 실패가 나머지를 중단시키지 않는다 / 보고서에 실제 병렬 수를 적는다
- **F-02** — 타임박스에 시작점이 없어 판정 불가능했다. 「T0 = 계획 커밋 시각」, 45분 소프트 마감, 60분 하드 마감으로 못박음
- **F-03** — 브랜치 규칙이 실제 환경과 이미 충돌했다 (직전 주행에서 실행자가 문서에 없는 규칙을 즉석에서 발명했다). 지정 브랜치 우선 → `conductor/<slug>` → 번호 증가 순서로 명문화하고, **푸시 실패는 "막힘"이 아니라는 것**을 추가. 여기서 멈추면 결과가 통째로 사라진다
- **F-04** — 사용자가 이미 자리를 뜬 상태에서 킥오프 질문을 던지면 무한 대기하고, 아이러니하게 "질문 0회" 지표는 통과한 것처럼 보였다. 무응답 기본값 3개를 명시
