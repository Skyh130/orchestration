# 주행 기록: dev-kickoff 트리거 테스트

- **일시**: 2026-09-01
- **과제**: `개발시작하기`(dev-kickoff) 스킬의 트리거 테스트를 만들고 실행한다
- **맥락**: Sprint 1 / S1-06 리허설 주행. conductor 뼈대가 실제로 도는지 측정하는 것이 목적이다
- **상태**: 완료 (18/20 통과)

## 킥오프

세 질문의 답이 이미 레포 문서에 있어 **아무것도 묻지 않았다.**

1. 무엇이 완성되어야 하나 → 트리거 테스트 세트 + 자동 실행 러너 + 판정 결과 (`docs/stories/sprint-1.md` S1-06)
2. 완료를 무엇으로 판단하나 → 켜져야 할 문장과 안 켜져야 할 문장이 각각 판정되어 파일로 남는다
3. 건드리면 안 되는 것 → `docs/prd.md`, `docs/sprints.md`, `docs/stories/` (합의된 기획 문서)

## 실행 계획

| 레인 | 작업 | 쓰기 대상 | 완료 기준 |
|---|---|---|---|
| A | should-trigger 쿼리 10개 작성 | `evals/dev-kickoff/triggers.json` | 표현이 서로 다른 10개, 스킬명 직접 언급 없는 것 포함 |
| B | should-not-trigger 쿼리 10개 작성 (근접 오답 위주) | `evals/dev-kickoff/triggers.json` | 키워드는 겹치나 실제로는 다른 것을 원하는 10개 |
| C | 자동 러너 작성 | `scripts/trigger_test.py` | 각 쿼리를 판정해 결과 파일과 통과율을 낸다 |
| D | 실행 및 판정 | `evals/dev-kickoff/results.*` | 20개 전부 판정, 오답 목록 확보 |

- A와 B는 같은 파일에 쓰므로 **한 레인으로 합친다** (레인 규칙: 같은 파일 = 같은 레인).
- C는 쓰기 대상이 겹치지 않아 병렬 가능.
- D는 A·B·C의 산출물이 모두 필요하므로 **직렬**.

## 검증 방법

작업 성격이 "스크립트·도구"이므로 실제로 한 번 돌려서 출력을 본다. 러너가 20개를 전부 판정하고 통과율을 내면 통과.

## 타임박스

30~60분. 초과 시 거기까지의 결과를 이 파일에 남기고 중단한다.

# 실행 결과

## 만든 것

- `evals/dev-kickoff/triggers.json` — 트리거 테스트 세트 20개 (켜져야 함 10 / 켜지면 안 됨 10)
- `scripts/trigger_test.py` — 자동 러너. 판정자를 병렬 5개로 굴려 통과율·재현율·정밀도를 낸다
- `evals/dev-kickoff/results.json`, `results.md` — 판정 결과
- 부수 산출물: `.claude/skills/conductor/SKILL.md` (S1-01~S1-05 본체)

**결과: 20건 중 18건 통과 (90%). 판정 오류 0건. 소요 27초.**

| 지표 | 값 |
|---|---|
| 켜져야 할 때 켜진 비율 | 80% (8/10) |
| 켜지면 안 될 때 안 켜진 비율 | 100% (10/10) |

## 내린 가정과 결정

| 결정 | 근거 |
|---|---|
| 트리거 판정을 실제 세션 실행이 아니라 **판정자 프롬프트**로 대신했다 | 실제 실행은 세션당 수 분이 걸려 20건에 타임박스를 초과한다. 실물의 근사치이며 이 한계는 아래 '막힌 것'에 적었다 |
| 판정자를 **레포 밖 임시 디렉터리**에서 돌린다 | 레포 안에서 돌리면 이 레포의 스킬들이 판정자 컨텍스트에 딸려 들어가 판정이 오염된다 |
| 켜지면 안 되는 쿼리를 **근접 오답 위주**로 골랐다 | 명백히 무관한 문장("피보나치 함수 짜줘")은 아무것도 검증하지 못한다 |
| 병렬 판정 수를 5로 잡았다 | conductor의 동시 실행 상한(3~5)과 같은 값을 써서 규칙을 실물로 검증했다 |
| 발견된 dev-kickoff 설명 결함을 **고치지 않고 보고만** 했다 | 이번 과제는 "테스트를 붙이는 일"이지 "스킬을 고치는 일"이 아니다. 스스로 범위를 넓히지 않는다는 원칙을 따랐다 |
| 주행 브랜치를 `conductor/<slug>`가 아니라 세션 지정 브랜치에 커밋했다 | 이 세션은 `claude/dev-kickoff-workflow-9djh9q` 로 푸시하도록 지정되어 있다. 지정 브랜치가 우선한다 |
| 에이전트별 모델 선택 규칙을 conductor에 추가했다 | 주행 중 사용자가 추가 요구를 보냈다: 기본 Sonnet, 고맥락 추론은 Opus, 기계적 작업은 Haiku |

## 막힌 것

- **1차 실행에서 2건이 판정 불가**로 나왔다. 원인은 프록시 TLS 오류였는데, 러너가 이것을 "오답"으로 세고 있었다. **인프라 장애와 스킬 품질이 한 숫자에 섞이면 통과율이 무엇을 뜻하는지 알 수 없게 된다.** 러너를 고쳐 오류를 별도로 세고 최대 2회 재시도하도록 했다 (재시도 상한은 conductor 규칙과 같은 값). 재실행에서 오류 0건.
- **판정자 방식은 실물의 근사치다.** 실제 세션에서는 대화 맥락과 다른 스킬과의 경쟁이 작용하므로 결과가 달라질 수 있다.
- **서브에이전트 팬아웃을 실제로 쓰지 않았다.** 이번 주행은 지휘자가 레인을 직렬로 처리했다. 즉 S1-02의 레인 분리 규칙은 문서로만 존재하고 실물로 검증되지 않았다. **Sprint 1에서 가장 중요한 미검증 항목이다.**

## 다음 추천

1. **실제 팬아웃 주행을 한 번 해야 한다.** 서브에이전트를 3~5개 띄워 레인 분리와 통합이 실물로 도는지 확인. Sprint 2로 넘어가기 전에 이것부터.
2. **dev-kickoff 설명에 빠진 표현 두 갈래를 보강**한다. 실패한 2건이 같은 결함을 가리킨다:
   - #10 `개발 계획`, `로드맵` — 설명에 이 단어들이 없다
   - #8 `인수조건`, `sprint 1` 같은 구체적 실행 요청 — "코드만 작성하면 되는 작업엔 쓰지 말 것"이라는 배제 문구가 과하게 작동한 것으로 보인다
3. **트리거 테스트를 Sprint 2 검증 게이트의 첫 적용 대상으로 삼는다.** 종료 코드로 합격/불합격이 나오므로 게이트에 그대로 물릴 수 있다.
4. 모델 선택 규칙이 방금 들어갔으니, 다음 주행에서 **레인별 모델 배정이 실제로 토큰을 아끼는지** 측정한다.
