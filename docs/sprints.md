# 개발 계획: conductor (자율 오케스트레이션 스킬)

> 기준 PRD: `docs/prd.md` · 상태: 초안 v0.1

## 확정된 운영 결정

이 결정들은 모든 스프린트에 공통으로 적용된다.

- **첫 리허설 과제**: 이 레포 안의 실제 소과제 — `개발시작하기` 스킬에 테스트 케이스를 붙이는 일. 조사·작성·검증이 섞여 있어 리허설로 적당하고, 30~60분 타임박스를 실측할 수 있다.
- **재시도 상한**: 같은 작업 2회까지. 3번째에는 보고하고 멈춘다. (우회 금지 원칙과 같은 뿌리)
- **에이전트 정의 개정**: 자동 커밋한다. git 이력이 남아 되돌리기 쉽고, 사용자가 없는 동안 승인 대기로 멈추지 않는다.
- **결과 보고서 위치**: `docs/runs/YYYY-MM-DD-<과제slug>.md` 로 커밋한다. 컨테이너가 회수돼도 남고, Sprint 4의 자기개선이 쓸 근거 데이터가 된다.

## 전체 구성 원칙

1. **리스크 선점** — PRD가 지목한 최대 실패 모드("빠르지만 틀린 결과")를 앞으로 당긴다.
2. **얇게 관통 먼저** — 완성도보다 "끝까지 한 바퀴 도는가"를 먼저 증명한다. 사용자의 선개발 후업그레이드 방식과 맞춘다.
3. **상상으로 스키마 짜지 않기** — 자산화·자기개선은 실제로 에이전트를 굴려본 뒤에 한다.
4. 각 스프린트는 끝에 **보여줄 수 있는 것**이 남는다.

---

## Sprint 1 — 걸어다니는 뼈대 (Walking Skeleton)

- **목표**: 자리를 비운 사이 한 번 굴렸을 때, 돌아오면 브랜치에 결과물과 보고서가 있다. 딱 한 번, 얇게.
- **포함 작업**
  - `conductor` 스킬 v0.1 골격 작성 (킥오프 → 분해 → 병렬실행 → 통합 → 커밋/푸시 → 보고)
  - 작업 분해 규칙: 무엇을 병렬로 돌리고 무엇을 직렬로 둘지
  - 병렬 레인 분리 규칙 (같은 파일을 두 에이전트가 건드리지 않게)
  - 에이전트 브리핑 템플릿 — 콜드 스타트를 전제로 무엇을 떠먹여 보낼지
  - 결과 보고서 포맷 v1 (만든 것 / 내린 가정 / 막힌 것 / 다음 추천) → `docs/runs/`에 커밋
  - 리허설 주행: `개발시작하기` 스킬에 테스트 케이스 붙이기 (무감독 1회)
- **완료 기준(DoD)**: 사용자 질문 0회로 과제 1건 완주 → 브랜치에 커밋된 결과물 + 보고서. 실패해도 "어디까지 했는지"가 보고서에 남는다.
- **의존**: 없음
- **이번에 걷어내는 리스크**: 팬아웃과 통합이 실제로 굴러가는가. 이게 안 되면 나머지 전부가 무의미하다.

## Sprint 2 — 검증 게이트

- **목표**: 자율 실행 결과가 틀렸을 때, 사용자 없이도 그걸 잡아낸다.
- **포함 작업**
  - 작업 성격별 검증 수준 정의 (코드=테스트 실행 / 조사=출처 교차확인 / 문서=독립 리뷰어 에이전트)
  - 검증 실패 시 재시도 정책: 같은 작업 2회까지, 3번째는 보고 후 중단
  - 타임박스 초과 시 "여기까지" 부분 결과 보존 절차
  - 우회 금지 원칙 구현 — 막히면 덮지 말고 보고하고 멈춘다
  - 통합 단계 충돌 처리
- **완료 기준(DoD)**: 일부러 틀린 결과를 내는 상황을 만들었을 때 게이트가 그것을 잡아 재시도하거나 보고서에 명시한다.
- **의존**: Sprint 1
- **이번에 걷어내는 리스크**: "빠르지만 틀린" 결과. PRD 기준 최대 실패 모드.

## Sprint 3 — 에이전트 자산화

- **목표**: 한 번 잘 작동한 에이전트가 다음에도 재사용된다.
- **포함 작업**
  - `.claude/agents/*.md` 저장 규격 확정
  - 레지스트리: 버전 / 마지막 개정 이유 / 알려진 약점 / 사용 이력
  - 재사용 vs 신규 생성 판단 규칙
  - 에이전트 정의 작성 가이드 (Sprint 1~2에서 실제로 써본 브리핑을 근거로)
  - 프로젝트별 덮어쓰기 규칙
- **완료 기준(DoD)**: 새 과제를 시켰을 때 지휘자가 기존 자산을 먼저 뒤지고, 맞는 게 있으면 재사용, 없으면 새로 만들어 자산에 추가한다.
- **의존**: Sprint 1, 2
- **왜 여기인가**: 앞에서 실제로 에이전트를 만들어봐야 무엇을 자산화할 가치가 있는지 안다.

## Sprint 4 — 자기 개선 루프

- **목표**: 같은 실패가 두 번 반복되지 않는다.
- **포함 작업**
  - 실행 기록 남기기 (어떤 에이전트가 무엇에 실패했는지)
  - 반복 실패 감지 규칙
  - 에이전트 정의 개정 → 버전 올리기 → 자동 커밋
  - 개정 이력을 레지스트리에 반영
  - 개정이 오히려 나빠졌을 때 되돌리는 절차
- **완료 기준(DoD)**: 특정 에이전트를 반복 실패시켰을 때 지휘자가 스스로 정의를 고치고 버전을 올려 커밋한다.
- **의존**: Sprint 2(실패 데이터), Sprint 3(레지스트리)

## Sprint 5 — 자율성 굳히기 & 실전 투입

- **목표**: 진짜로 자리를 비우고 돌려도 되는 상태로 만든다.
- **포함 작업**
  - 킥오프 인터뷰 정형화 (질문이 허용되는 유일한 구간을 짧고 날카롭게)
  - 판단 원칙 내장: 기존 관례 우선 > 단순한 쪽 > 새 의존성 회피, 막히면 보고 후 중단
  - 자율 경계 강제: 커밋·브랜치 푸시까지, 머지·배포는 보고만
  - 결정 로그 — 실행 중 내린 모든 판단을 보고서에 남긴다
  - 실제 프로젝트로 무감독 실전 주행
- **완료 기준(DoD)**: 사용자가 자리를 비운 상태에서 과제 1건 완주. 질문 0회, 결과물 커밋됨, 결정 로그로 무엇을 왜 그렇게 했는지 추적 가능.
- **의존**: Sprint 1~4
