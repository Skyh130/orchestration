# PRD: 자율 오케스트레이션 스킬 (코드네임: conductor)

> 상태: 초안 v0.1 · 작성 방식: 개발시작하기(dev-kickoff) 인터뷰

## 1. 한 줄 요약

기획만 짧게 함께 한 뒤, 사용자가 자리를 비워도 지휘자(Claude)가 **그 프로젝트에 맞는 에이전트 군단을 직접 만들어** 개발·테스트·조사를 병렬 자율 수행하고, 사용자가 돌아왔을 때 **검증된 결과물 + 내린 결정의 기록**을 바로 보게 하는 스킬.

## 2. 문제 정의

- 하려는 일이 매번 달라서, 미리 만들어둔 범용 에이전트가 잘 안 맞는다.
- 병렬로 굴리고 싶지만 지휘가 부실하면 5개가 **같은 오해를 5배 속도로** 저지른다.
- 지금 구조는 사용자가 붙어서 계속 답을 줘야 굴러가서, 자리를 뜰 수가 없다.
- 잘 작동한 에이전트도 세션이 끝나면 휘발된다. 축적이 안 된다.

## 3. 대상 사용자

1인 개발자(본인). 기획 의도는 명확하지만 실행에 붙어 있을 시간이 없고, 결과를 빠르게 받아 그걸 토대로 다음 판을 짜는 방식으로 일한다.

## 4. 핵심 사용 흐름

0. 사용자가 스킬을 호출하고 하고 싶은 일을 설명한다.
1. **킥오프(질문이 허용되는 유일한 구간)** — 목표, 완료 조건, 판단 기준을 짧게 확인한다.
2. **실행 계획** — 작업을 분해하고, 필요한 역할을 식별하고, 자산에 있으면 재사용 / 없으면 새로 만들고, 서로 파일이 겹치지 않는 병렬 레인으로 배치한다. 승인은 받지 않고 계획을 기록만 한다.
3. **자율 실행** — 병렬 팬아웃. 자료·도구가 필요하면 능동적으로 조사한다.
4. **검증 게이트** — 테스트 실행 또는 교차 확인을 강제한다. 실패하면 재시도하고 원인을 남긴다.
5. **통합 → 커밋 → 브랜치 푸시.**
6. **결과 보고서** — 만든 것 / 내가 내린 가정과 결정 / 막힌 것 / 다음 루프 추천.
7. **자산 갱신** — 이번 실행에서 각 에이전트가 어땠는지 기록하고, 같은 실패가 반복되면 정의를 고쳐 버전을 올린다.

## 5. 범위

### MVP에 포함

- 스킬 본체: 킥오프 → 계획 → 병렬 실행 → 검증 → 통합 → 보고 의 6단계 루프
- 에이전트 자산화: `.claude/agents/*.md` + 버전/약점/사용이력 레지스트리
- 재사용 vs 신규 생성 판단 규칙
- 병렬 레인 분리 규칙 (파일 충돌 회피)
- 검증 게이트 (작업 성격별로 수준이 다름)
- 결과 보고서 고정 포맷
- 판단 원칙 내장: 기존 관례 우선 > 단순한 쪽 > 새 의존성 회피, 그리고 막히면 우회 대신 보고 후 중단
- 자기 개선: 실행 결과를 근거로 에이전트 정의 개정

### 나중에 (Out of scope for now)

- PR 자동 생성 / 머지 / 배포
- 에이전트 성능 정량 벤치마크 자동화
- 여러 레포 간 자산 공유 레지스트리
- 자리 비운 사이 진행 상황 실시간 알림

### 이번엔 하지 않는 것

- 에이전트 간 직접 통신 (구조적으로 불가능. 모든 소통은 지휘자를 경유)
- 되돌리기 어려운 행동(머지, 배포, 외부 발행)의 무승인 실행

## 6. 성공 기준

- 자리를 비운 사이 한 번 시켜두면, 돌아왔을 때 **브랜치에 커밋된 동작하는 결과물 + 보고서**가 있다.
- 첫 결과물까지 30~60분. 그 안에 못 끝내면 거기까지의 결과를 보고한다 (빈손 금지).
- 실행 중 사용자에게 던진 질문 **0회**.
- 같은 실패가 두 번 반복되지 않는다 = 에이전트 버전업이 실제로 작동한다.
- 3회 이상 재사용된 에이전트가 생긴다 = 자산화가 실제로 작동한다.

## 7. 제약과 전제

- 실행 환경: 원격 세션 기준. 컨테이너가 회수되므로 **결과는 반드시 커밋·푸시로 보존**한다.
- 자율 경계: 파일 수정 + 로컬 커밋 + 브랜치 푸시까지. PR/머지/배포는 보고만.
- 에이전트는 대화 맥락 없이 차갑게 시작한다 → 브리핑 품질이 성패를 가른다.
- 에이전트끼리 대화할 수 없다 → 조율이 필요한 일은 병렬로 쪼개면 오히려 느려진다.
- `가정:` 서브에이전트는 다시 서브에이전트를 부를 수 없다. 팬아웃 지점은 지휘자 하나뿐이다.
- `가정:` 에이전트 자산은 이 `orchestration` 레포에 모으고, 프로젝트별 덮어쓰기를 허용한다.

## 8. 데이터 / 외부 연동

- git / GitHub (브랜치 푸시까지)
- 웹 조사 (능동 리서치용)
- 로컬 파일시스템
- 민감정보·개인정보·결제 없음

## 9. 비기능 요건

- 첫 결과물 30~60분 타임박스.
- 부분 실패해도 부분 결과물은 보존된다.
- `가정:` 동시 실행 에이전트 상한 3~5 (토큰·안정성 고려)

## 10. 리스크와 미해결 질문

- **리스크: 검증 게이트가 약하면 "빠르지만 틀린" 결과가 나온다.** 이 프로젝트에서 가장 큰 실패 모드.
- **리스크: 팬아웃 지점이 지휘자 하나뿐**이라 지휘자의 브리핑이 병목이자 단일 실패점이다.
- **리스크: 30~60분 타임박스와 완전 자율이 충돌**할 수 있다. 막히면 (e) 원칙으로 보고 후 중단해서 해소한다.
- 미해결: 동시 실행 상한을 몇으로 둘지 (가정 3~5)
- 미해결: 자리를 비운 사이 진행 상황을 어떻게 알릴지 (MVP 밖)
