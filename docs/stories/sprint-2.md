# Sprint 2 스토리 — 검증 게이트

> 목표: 자율 실행 결과가 틀렸을 때, 사용자 없이도 그걸 잡아낸다.
> 상태: 확정 v1.0
> 입력: `docs/reviews/conductor-v0.1.md` 의 F-05 ~ F-08, 그리고 Sprint 1 회고

---

### S2-01 — 검증 수준 매트릭스와 검증 수단 부재 처리
- **사용자 스토리**: 사용자로서 작업 성격에 맞는 검증이 걸리길 바란다, 코드와 조사에 같은 잣대를 대면 둘 다 헛돌기 때문에.
- **인수 조건**
  - Given 산출물이 코드 / When 검증 / Then 레포의 테스트·린트·타입체크를 **실제로 실행**하고 통과 로그를 확인한다
  - Given 산출물이 스크립트·도구 / When 검증 / Then 한 번 돌려서 출력을 본다
  - Given 산출물이 조사 결과 / When 검증 / Then 출처를 두 곳 이상 교차 확인한다
  - Given 레포에 검증 수단이 하나도 없음 / When 검증 / Then 최소 스모크 검사를 직접 만들어 돌린다
  - Given 검증 도구 자체가 고장남(설치 실패·환경 오류) / When 검증 / Then 산출물의 실패로 세지 않고 "검증 불가"로 분류해 보고서에 남긴다
- **기술 메모**: 근거 F-07. 인프라 장애를 품질 실패로 세면 숫자가 뜻을 잃는다 — 이미 1차 주행에서 겪은 실패다.
- **크기**: M · **의존**: 없음

### S2-02 — 미검증 산출물의 처분
- **사용자 스토리**: 사용자로서 검증을 못 마친 결과물도 잃고 싶지 않다, 그러나 검증된 것과 섞이는 것은 더 싫다.
- **인수 조건**
  - Given 하드 마감으로 검증 미완 / When 통합 / Then 산출물을 버리지 않고 **검증된 것과 별도 커밋**으로 분리해 남긴다
  - Given 미검증 커밋 / When 보고서 작성 / Then 어떤 파일이 미검증인지, 무엇이 남았는지 명시한다
  - Given 검증에서 명백히 틀린 것으로 판명 / When 통합 / Then 커밋하지 않고 실패로 기록한다 (미검증과 오검증은 다르다)
- **기술 메모**: 근거 F-05. "성공 결과는 커밋한다"와 "검증 없이 통합하지 않는다"가 부딪히는 지점.
- **크기**: S · **의존**: S2-01

### S2-03 — 계획 밖 파일 변경 탐지
- **사용자 스토리**: 지휘자로서 에이전트가 배정받지 않은 파일을 고쳤는지 알고 싶다, 레인 분리가 지켜졌는지는 확인해야 아는 것이지 믿을 것이 아니기 때문에.
- **인수 조건**
  - Given 모든 레인 회수 완료 / When 통합 직전 / Then 실제 변경 파일 목록과 계획의 쓰기 대상 목록을 대조한다
  - Given 계획에 없는 파일이 변경됨 / When 대조 / Then 되돌리지 않고 **별도 커밋으로 분리**한 뒤 보고서에 명시한다
  - Given 금지 목록의 파일이 변경됨 / When 대조 / Then 해당 변경을 되돌리고 어느 레인이 어겼는지 기록한다
- **기술 메모**: 근거 F-08. 계획 밖 변경이 옳은 경우도 있으므로 일괄 되돌림은 위험하다. 다만 명시적 금지 목록은 다르다.
- **크기**: M · **의존**: 없음

### S2-04 — 재시도의 세는 단위
- **사용자 스토리**: 지휘자로서 "2회"가 무엇의 2회인지 알고 싶다, 세는 단위가 없으면 상한이 상한이 아니기 때문에.
- **인수 조건**
  - Given 한 레인이 실패 / When 재시도 / Then 재시도 횟수는 **레인 단위**로 센다 (에이전트 호출 단위가 아니다)
  - Given 실패 원인이 인프라(타임아웃·API 오류) / When 재시도 / Then 이 횟수는 상한에 넣지 않는다
  - Given 2회 재시도 후에도 실패 / When 처리 / Then 그 레인을 실패로 확정하고 나머지 레인은 계속 진행한다
  - Given 재시도 시 모델을 올림 / When 처리 / Then 상한 안에서 한 번만 허용한다
- **크기**: S · **의존**: 없음

### S2-05 — 검증자와 실행자의 분리
- **사용자 스토리**: 사용자로서 만든 사람이 자기 결과를 채점하지 않길 바란다, 자기가 찾은 문제를 자기가 정당화하기 때문에.
- **인수 조건**
  - Given 자동 검증 수단이 있는 산출물(코드·스크립트) / When 검증 / Then 별도 검증자를 붙이지 않는다 (테스트가 그 역할이다)
  - Given 자동 검증이 불가능한 산출물(문서·설계·기획) / When 검증 / Then **수정 권한이 없는 별도 검증자**를 붙인다
  - Given 검증자 브리핑 / When 작성 / Then 쓰기 대상은 리뷰 파일 하나뿐이고 검토 대상 파일은 금지 목록에 있다
- **기술 메모**: Sprint 1 팬아웃 주행에서 실증된 패턴. 레인 B에 수정 권한을 주지 않은 것이 유효했다.
- **크기**: S · **의존**: 없음

### S2-06 — 게이트 실물 검증 주행
- **사용자 스토리**: 사용자로서 게이트가 진짜로 잡는지 보고 싶다, 문서에만 있는 규칙은 Sprint 1에서 이미 한 번 배신했기 때문에.
- **인수 조건**
  - Given 일부러 틀린 산출물을 내도록 심은 레인 / When 주행 / Then 게이트가 그것을 잡아 재시도하거나 보고서에 명시한다
  - Given 계획 밖 파일을 건드리도록 심은 레인 / When 통합 직전 대조 / Then 탐지되어 별도 처리된다
  - Given 주행 종료 / When 확인 / Then 정상 레인의 결과는 그대로 살아 있다 (게이트가 멀쩡한 것까지 죽이지 않는다)
- **크기**: L · **의존**: S2-01 ~ S2-05
